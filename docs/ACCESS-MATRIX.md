# Access matrix — роли и доступ к функциям

**Status:** DRAFT v3 — согласовано, идёт реализация.

**Как редактировать:** правьте **только Table A (бандлы ролей)** и **Table B
(гейты функций)**. Матрица в §4 — **генерируется** из них; руками не править.
Если галочка выглядит неправильно — чинить нужно бандл или гейт, а не галочку.

---

## 1. Как устроен доступ

Четыре независимые оси. Бандл роли управляет только второй.

| Ось | Что это | Кто задаёт |
|---|---|---|
| `is_platform_admin` | Флаг. Сотрудники ИСПУМ. Обходит всё. | Платформа |
| **Грант в оргдереве** | `(level) × (domain) × (поддерево)` — это и есть бандл роли | Админ организации / админ поддерева |
| `program_access` | Выводится отдельно из **типа оргединицы** (§5) | Неявно |
| Тариф | free / pro / institution — ортогонально ролям | Биллинг |

**Уровни:** `view` < `edit` < `admin`
**Единица назначения:** грант действует на свою оргединицу **и всё, что ниже**.
Один и тот же бандл на корне и на кафедре — это разница между Проректором и Завкафедрой.

### Домены (4 + wildcard)

| Домен | Что закрывает |
|---|---|
| `platform` | `edit` — стратегия развития · `admin` — структура организации (CRUD) |
| `curriculum` | Содержание: ОП, РПД, критерии, рубрики, компетенции |
| `teaching` | Учебный процесс: проверки, аналитика, ростер, руководство |
| `umu` | 🆕 Инструменты УМУ/УМЦ: Мониторинг РПД |
| `all` | Wildcard — только корневой админ |

> **Почему `umu`:** ЗК должен создавать Критерии (`curriculum:edit`), но не видеть
> Мониторинг РПД — который был на том же `curriculum:edit`. Один домен не может
> разделить две функции на одном уровне.

> **Почему `platform` двухуровневый:** Стратегия развития (`edit`) и Структура
> (`admin`) — разные вещи. Проректор правит стратегию, но не трогает оргструктуру.

> **Почему у `curriculum` есть ось ТИПА единицы (2026-07-28):** сам домен
> обозначает предметную область («content authority»), а не орг-уровень —
> им законно владеют и РОП (единица `program`), и ЗК (единица `department`).
> Но «Критерии/Рубрики» (институционская курация) — это работа
> кафедры/института, а не программы: `curriculum:view/edit` сам по себе не
> различает, на единице какого ТИПА сидит грант. `requireDomainOnUnitTypes`
> (`services/accessScope.ts`) добавляет этот фильтр только для
> Критериев/Рубрик — остальные `curriculum`-гейты (РОП Студия, Готовность
> УМК до 2026-07-28) не трогает.

**Отклонённые домены:** `analytics`/`reports` (= масштаб, задаётся единицей
назначения), `research` (нет функций), `umc:lead/member` (= уровень + поддерево),
`staff` (УМУ/УМЦ ростер не нужен — вернуться с Feature W), `syllabus` (доступ
преподавателя к своей РПД — это владение, а не поддерево; решается
ответственным за дисциплину в маршруте согласования, §7).

## 2. Table A — Каталог ролей ✏️ РЕДАКТИРУЕТСЯ

Бандл — набор пар `(домен, уровень)`. **Единица выбирается при назначении**, не здесь.

| Роль | Код | Бандл | Назначается на | Статус |
|---|---|---|---|---|
| Ректор | **РЕК** | `teaching:view`, `curriculum:view` | institution | ✅ |
| Проректор по учебной работе | **ПР** | `teaching:view`, `curriculum:view`, `platform:edit` | institution / governance | ✅ |
| Проректор по научной работе | **ПР-НАУ** | *(нет — нет функций)* | governance | ⏸️ |
| Директор института | **ДИ** | `teaching:edit`, `curriculum:view`, `platform:admin` | division / cluster | ✅ |
| Декан факультета | **ДЕК** | `teaching:edit`, `curriculum:view` | division | ✅ |
| Заведующий кафедрой | **ЗК** | `teaching:admin`, `curriculum:edit` | department | ✅ |
| Руководитель ОП (РОП) | **РОП** | `curriculum:admin`, `teaching:view` | program / program_direction | ✅ |
| Руководитель полигруппы | **РПГ** | `curriculum:edit` | cluster | ✅ |
| Методист / Нач. УМУ | **УМУ** | `umu:edit`, `curriculum:edit` | admin_office / institution | ✅ |
| Руководитель УМЦ | **РУМЦ** | `umu:admin`, `curriculum:admin` | admin_office (УМЦ) | ✅ |
| Методист УМЦ | **МУМЦ** | `curriculum:edit` | admin_office (под-единица УМЦ) | ✅ |
| Преподаватель | **ПП** | *(нет грантов)* | — | ✅ |
| Администратор организации | **ОА** | `all:admin` | institution (корень) | ✅ |

⏸️ = роль в каталоге, грантов пока нет — появятся вместе с функциями.

> ✅ **Решено 2026-07-29 (было открытым вопросом): ограничение снято, не
> оставлено.** Раньше `role='admin'` всегда принудительно получал
> `domain='all'` (Phase 1) — это и была причина инцидента: `daniel@knity.ru`
> получил роль «Администратор» на своей единице `program` и оказался с
> институционально-широким доступом к Структуре/УМУ/Критериям вместо доступа
> только к своей программе. Теперь `admin` масштабируется так же, как
> `edit`/`view` — по поддереву единицы, на которую выдан. `domain='all'` при
> `role='admin'` теперь принимается **только** на корне организации (реальный
> админ организации); `routes/orgUnits.ts`'s `POST /roles` отклоняет эту
> комбинацию на любой другой единице. `curriculum:admin`/`umu:admin` теперь
> действительно выдаются (РОП и РУМЦ в Table A получают именно их) — как и
> раньше, `admin` не открывает ничего сверх `edit` нигде, кроме гейта
> Структуры на `platform:admin`, так что смены поведения для существующих
> `edit`-грантов нет.

**Иерархия УМЦ — поддеревом, не доменом:** РУМЦ на единице УМЦ, МУМЦ на
под-единице. Containment сам даёт РУМЦ всё, что есть у МУМЦ.

**Преподаватель:** доступ к своим предметам — через владение (`courses.teacher_id`),
не через дерево. Право править РПД конкретной дисциплины появится вместе с
маршрутом согласования (§7) как «ответственный за дисциплину».

## 5. Программы — отдельная ось (`program_access`)

Выводится из **типа оргединицы**, а не из бандла:

| Тип единицы | Результат |
|---|---|
| `institution` (корневой админ) | все ОП, чтение+запись |
| `governance` / `admin_office` | все ОП (запись при `edit`+, чтение при `view`) |
| `cluster` / `division` / `department` / `program` | только ОП своего поддерева |

| Роль | Программы |
|---|---|
| РЕК, ПР | все ОП, **только чтение** |
| ДИ, ДЕК, ЗК, РПГ | своё поддерево |
| РОП | своя ОП |
| УМУ, РУМЦ, МУМЦ | все ОП |
| ПП | нет |

> 🔧 **Фикс (в работе):** `getProgramAccessScope` учитывал только `admin`/`edit`
> и игнорировал `view` — из-за чего РЕК и ПР получали **ноль** доступа к
> программам. Добавляется read-only ветка.

## 6. Публикация отчёта РУМЦ → руководство

Ректор и Проректор **не получают постоянный грант** на Мониторинг РПД. Вместо
этого РУМЦ/УМУ явно публикует снимок отчёта («Поделиться с руководством») — он
появляется у руководства как датированный отчёт только для чтения.

Это повторяет реальный процесс (сегодня — Excel по почте) и оставляет контроль
над тем, *что* и *когда* показывать, у РУМЦ.

## 7. Маршрут согласования РПД → внутри РОП Студии

**Решено:** рабочий процесс *Преподаватель → сдаёт РПД → РОП → передаёт в УМЦ →
РУМЦ видит статистику* строится как часть **РОП Студии**.

📄 **Полная спецификация: [RPD-WORKFLOW.md](RPD-WORKFLOW.md)** — состояния,
схема данных, новые возможности и их гейты.

Сегодня есть артефакты, но нет состояний:

| Есть | Нет |
|---|---|
| `program_documents` — загруженный РПД | Статус: черновик / сдан / на проверке / согласован |
| `program_document_reviews` — ИИ-проверка покрытия | Человеческий вердикт: кто, когда, что решил |
| Готовность УМК — «загружен, проверен ИИ» | Ответственный за дисциплину; очередь проверки; на каком этапе застрял |

Здесь же появляется «ответственный за дисциплину» — то, что заменило отклонённый
домен `syllabus`.

## 8. Правила назначения (согласовано)

| Действие | Кто может |
|---|---|
| **Определить** роль (что она даёт) | Только корневой админ организации / платформа |
| **Назначить** существующую роль | Делегируется — админ поддерева, в пределах поддерева |
| Создать админа организации | Только платформа |
| Изменить определение роли | Переприменяется ко всем носителям; «затронет N человек» + аудит |

**Инвариант:** роль не содержит привязки к единице → назначающий не выдаст больше,
чем имеет сам на этой единице (containment `canActOnUnit`).

## 9. План реализации

| # | Шаг | Статус |
|---|---|---|
| 1 | Фикс схлопывания в `getAccessScope` (multi-hat теряет широкий грант) | 🔨 |
| 2 | Фикс `program_access` — учитывать `view`-гранты | 🔨 |
| 3 | Домен `umu` + разделение гейтов Мониторинга РПД + `platform:edit` для стратегии | 🔨 |
| 4 | Маршрут согласования РПД в РОП Студии + публикация отчёта (§6, §7) | 📋 |
| 5 | Каталог ролей + назначение (Table A как данные, а не документ) | 📋 |

**Почему роли последними:** бандл хорош ровно настолько, насколько стабильны
гранты, которые он собирает. Маршрут согласования введёт новые возможности
(«сдать», «вернуть», «согласовать», «поделиться»), которых сегодня нет — собирать
каталог до них значит пересобирать его сразу после.
